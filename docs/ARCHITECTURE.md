# هندسة مشروع مِعيار

## المبدأ

المشروع واجهة static، لا يحتاج خادمًا لتشغيل الواجهة. تُقدَّم ملفات HTML/CSS/JS مباشرة، بينما مزامنة البيانات تتم مع Google Apps Script وGoogle Sheets. لذلك يجب الفصل بين ملفات الواجهة والاختبارات والتوثيق وكود التكامل الخارجي.

## المسؤوليات الحالية

| المسار | المسؤولية |
| --- | --- |
| `index.html` | نقطة الدخول، metadata وروابط ملفات الواجهة |

| `js/app.js` | ملف JavaScript المجمّع الذي يحمّله المتصفح؛ يُولّد من ملفات المصدر ولا يُعدّل يدويًا |
| `assets/` | شعارات وصور العلامة التجارية |
| `site.webmanifest` و`favicon.svg` | بيانات تثبيت الموقع وأيقونته |

| `js/modules/10-google-sheets-sync.js` | تكامل Google Sheets وعقد البيانات الحالي |
| `js/modules/20-state-and-accounting.js` | تهيئة الحالة وتطبيعها ومحرك الحسابات |
| `js/modules/30-charts.js` | الرسوم البيانية |

| `scripts/build.js` | تجميع ملفات المصدر بالترتيب نفسه إلى `js/app.js` والتحقق من التطابق |
| `tests/` | اختبارات الانحدار للحسابات ووجود عناصر الواجهة |

## مسار البيانات

1. تُدخل المعاملات من الواجهة.
2. يُطبّق منطق التحقق والحساب داخل JavaScript.
3. تُرسل المعاملات إلى ورقة `DB_TRANSACTIONS`، وتُحفظ الإعدادات المشتركة في `SYS_APP_SETTINGS` منفصلة تمامًا.
4. يدمج Apps Script تغييرات الإعدادات على مستوى السجل ذي المعرّف الثابت، ثم تُحمّل المعاملات والإعدادات عند فتح الصفحة وأثناء المزامنة.
5. الاختبارات تتحقق من الحسابات وقواعد الأعمال الأساسية؛ ولا تحل محل اختبارات المتصفح الفعلية أو فحص صلاحيات نشر Apps Script.

## قواعد التطوير

- اعتبر معاملات Google Sheets والرصيد المحسوب بيانات حساسة؛ لا تغيّرها ضمن إعادة تنظيم ملفات أو تحسين بصري.
- احتفظ بمخطط الأعمدة الحالي A:L إلى أن يُصمّم إصدار ترحيل واختبارات له.
- افصل الإصلاح المالي عن التغيير الشكلي في pull request قدر الإمكان.
- أي ميزة جديدة يجب أن تضيف اختبارات للحالات الطبيعية والحدّية والفشل.
- حدّث توثيق `docs/` في نفس التغيير الذي يعدّل طريقة التشغيل أو مزامنة البيانات.

## ملفات JavaScript المصدرية

ملفات `js/modules/` هي مصدر التعديل. أما `js/app.js` فهو ناتج التجميع الذي يحمّله المتصفح.

- التجميع مجرد لصق للملفات بالترتيب المحدد في `scripts/build.js`؛ لا يغيّر الكود أو أسماء الدوال أو مخطط المعاملات.
- يحتفظ الموقع بملف JavaScript واحد وقت التشغيل، ولا يحتاج إلى خادم أو إلى تحميل ES modules من `file://`.
- بعد تعديل المصدر، شغّل `npm run build` ثم `npm run validate`.
- يتحقق `npm run validate` من أن `js/app.js` مطابق حرفيًا للمصدر، ومن صحة صياغة كل ملف ومن اختبارات الحسابات وعقد المعاملات.
- نُفّذ التقسيم الأول عبر حدود متتابعة من الملف القديم. أي إعادة توزيع للدوال أو تعديل في منطقها تكون خطوة مستقلة، وتتطلب اختبارات إضافية.

## المرحلة التالية: فصل المسؤوليات منطقيًا

التقسيم الحالي يحافظ على ترتيب المصدر القديم حرفيًا، ويُنتج نفس `js/app.js` دون تغيير وظيفي. لذلك لا تزال بعض المسؤوليات متجاورة داخل ملفات مصدر كبيرة نسبيًا.

يمكن لاحقًا إعادة تنظيمها إلى وحدات أصغر حسب الميزة، لكن لا يتم نقل الدوال أو تغيير ترتيب التهيئة إلا على مراحل، مع اختبارات تغطي الحالات المرتبطة بكل وحدة. كل مرحلة يجب أن تحافظ على:
- نفس نتيجة الحسابات قبل التغيير وبعده.
- نفس مفتاح التخزين المحلي وشكل سجلات المعاملات.
- نفس حقول وترتيب Google Sheets A:L.
- نفس سلوك الإضافة والتعديل والحذف والمزامنة.

أي تعديل في قواعد المحاسبة أو مخطط البيانات يجب أن يكون تغييرًا مستقلًا، وليس جزءًا من إعادة التنظيم.
